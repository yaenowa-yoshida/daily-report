業務改善の取り組み ／ 日報システム紹介

日報を、あとで書かない。

15分単位で「これからやる作業」を先に記録する、自作の日報システムです。
一日が終わる頃には、日報はもう出来上がっています。

案件A｜API設計
案件A｜レビュー
MTG｜週次定例
案件B｜改修
9:00 10:00 11:00
発表者：吉田 勝大 PowerShell 製・完全ローカル動作 利用マニュアル（Excel）

課題

日報の「よくある困りごと」

思い出せない

終業時にまとめて書こうとすると、午前中に何をしていたかはもう記憶が曖昧。日報の精度が日々落ちていく。

粒度が粗くなる

「終日：開発」のような一行になりがち。月次報告や工数集計に使おうとしても、案件別の内訳が出せない。

書くこと自体が負担

一日の最後に残る「重いタスク」になり、後回し・書き忘れが起きる。翌日まとめて書くと精度はさらに下がる。

原因はひとつ。「あとで、思い出して書く」から。

アプローチ

「思い出して書く」から、
「始める前に宣言する」へ

従来の日報

作業する → 記憶をたどる → 日報を書く

記録の品質が「記憶力」と「終業時の余力」に依存する。

この仕組み

次の作業を宣言する → 作業する（記録は済んでいる）

15分区切りごとに「これからやること」を選ぶだけ。記憶には一切頼らない。

日報は「書くもの」から「勝手に貯まるもの」へ。

全体像

一日の流れ

起動

デスクトップのアイコンをダブルクリック

朝いちばんに起動して「業務開始」を押した瞬間から記録が始まる。ショートカットは初回起動時にデスクトップへ自動で用意され、消えても起動のたびに作り直される。

日中

2つのウィンドウで運用

入力ウィンドウが15分区切りごとに現れ、次の作業を宣言。日報メニュー（常駐の小窓）からは編集・MTG予約がいつでもできる。

終業

表を確認して「締め」

業務終了は任意のタイミングでOK。一日の記録全体が表で表示され、最終確認・修正をして「締め」ボタンでCSVを保存。キャンセルすれば通常運転に戻る。

月次

報告書の元データが揃っている

15分粒度・案件別のCSVが日々貯まっているので、月次報告書への転記は集計するだけ。

画面① 入力ウィンドウ

15分ごとに、選ぶのは3つだけ

15分区切りごとに、これだけが出てくる。

  • 15分区切りのタイミングで自動表示。書きに行くのではなく、向こうから来る。 宣言した時間（15〜120分）のあいだは表示されない
  • 案件・作業内容は選択式。迷わず数秒で完了。
  • 新しい作業名は直接入力すればOK。次回から選択肢に自動追加される。
  • 休憩は長さを決めない。押すと「休憩中」の窓が出て待機し、戻って「休憩完了」を押した時点までが休憩として記録される。 15分未満なら記録なし。押し間違えてもデータは汚れない
  • MTG予約済みの時間帯には出てこない。会議の邪魔をしない。

画面② 日報メニュー

常駐の小窓から、いつでも5操作

× で閉じてもタスクトレイに常駐。右クリックでいつでも再表示。

「休憩」を押すと出る窓。戻って押した時点までが記録される。

  • 編集 — 日報ログのある日付を選び、時刻×案件×作業内容の表をその場で修正。 過去の日付も直せる（次のスライド）
  • MTG予約 — 当日の先の時間枠を、会議の予定で事前に確保。
  • 休憩 — 入力ウィンドウを待たずに休憩へ。戻って「休憩完了」を押した時点までが記録される。
  • 選択肢の編集 — 案件・作業内容の候補をその場で整理（後半のスライド）。
  • 業務終了 — いつでも締め処理へ。入力ウィンドウ・トレイアイコンからも同じ操作ができる。 3つの入口はどれも同じ表記・同じ挙動で揃えてある

画面③ 一覧編集

あとから直せるから、迷わず記録できる

「編集」で開く一日の記録表。業務終了時の確認画面も同じもの。

  • 日報ログのあるどの日付でも開ける。入力し忘れた枠の穴埋めも、過去日の修正もここで完結。
  • 「この行を入力欄へコピー」→「選択した行に入力」で、同じ作業をマウス操作だけで複製できる。 ドロップダウンを触らずに、まとまった時間の記録を一気に埋められる
  • 空欄にすればその枠の記録を削除。MTG予約の取り消しもここから行う。
  • 保存すると時刻順に並べ直してCSVを書き直す。 ExcelでCSVを開いて書式が変わっても、読み込み側で吸収するので壊れない

画面④ MTG予約

会議が始まる瞬間に、入力を求めない

15分ごとにウィンドウが出る仕組みの最大の弱点は「会議中に出てくること」。そこで、会議は先に枠を予約しておく方式にしました。

入力ウィンドウ表示
MTG予約済み（表示なし）
入力ウィンドウ再開
〜13:30 13:30〜14:30 14:30〜
  • 開始時刻・時間（30分か60分）・案件・作業内容を指定して先の枠を記録。
  • 予約した時間帯は入力ウィンドウがスキップされる。会議に集中でき、記録はすでに済んでいる。
  • 予定が消えたら「編集」で該当枠をクリアするだけ。

データ

成果物は、素直なCSV

1日1ファイル・1行=15分枠。UTF-8（BOM付き）なので Excel でそのまま開けます。

日報ログ\日報ログ_2026-07-31.csv
日付時刻案件作業内容
2026/07/319:00案件AAPI設計レビュー
2026/07/319:15案件AAPI設計レビュー
2026/07/319:30案件APRJ-12 商品ページ改修
2026/07/319:45社内週次定例MTG
2026/07/3112:00その他休憩
  • ピボット集計するだけで案件別・作業別の工数が出る。月次報告の元データに直結。
  • 休憩も1行として残るので、空白が「入力し忘れ」なのか「休んでいた」のか後から迷わない。
  • 特別なDBもクラウドも不要。ただのファイルなので壊れず、いつでも読める。 Excelで開いて保存し、日付の書式が変わっても読み込み側で吸収する

同じ2ファイルを画面から編集する「選択肢の編集」。

  • 案件.txt と 作業名.txt の2ファイルだけ。# でコメントも書ける。
  • 作業名は [案件名] の見出しでグループ化。選択中の案件の作業名（＋共通分）だけが選択肢に出る。
  • 表示のたびに再読込。メモ帳で編集すれば、次のウィンドウから即反映。
  • ウィンドウで直接入力した新しい作業名は、該当案件のセクションに自動追記される。 放っておいても候補は育つ。整理したくなったときだけ手を入れる
  • 「選択肢の編集」で、追加・名前変更・削除・並べ替え・別案件への移動が画面から可能。書き戻してもコメント行は残す。
  • 名前変更・削除で変わるのは次回からの選択肢だけ。過去のCSVは当時の表記のまま残す。

構成

中身は、このフォルダひとつ

インストールも設定画面もありません。このフォルダを丸ごと渡せば、そのまま動きます。

日報記録\ ├ 日報入力.bat起動用（デスクトップのショートカットの実体） ├ Nippo-Batch.ps1プログラム本体。修正するのはここだけ ├ ユーザーマニュアル.xlsx利用者向けの使い方 ├ ユーザーマニュアル生成.ps1↑を作り直すスクリプト（本文はこちらが持つ） ├ 日報システム紹介プレゼン.htmlこの資料 ├ README.md構成・保守メモ（引き継ぎ用） ├ 日報ログ\出力。1日1ファイルのCSV ├ 日報設定\案件.txt ／ 作業名.txt └ 画像\資料に貼る画面のスクリーンショット
  • フォルダごと持ち運べる — ログも設定も、スクリプトと同じ場所を見に行く。移動しても動く。
  • 人が読めるものしかない — CSVとテキストとPowerShell。専用の形式もデータベースもない。
  • 資料も同じ場所に置く — マニュアルとこの資料を一緒に渡せば、それだけで引き継げる。

この仕組みは、どう作ったか

私は元エンジニアなので、コードは読めますし、調べれば書けます。ただ、いまは開発が本業ではありません。
そこでClaude Code（対話型のAI開発ツール）と話しながら、書く側ではなく確かめる側に回って作りました。仕様書はつくっていません。

「何に困っているか」「どう動いてほしいか」を日本語で伝える。会社のルールを伝える。出てきたコードと画面に目を通し、違和感をそのまま言う。

何を作るか、どこで妥協するかは、使っている本人にしか決められない。AIは提案はするが、決めてはくれない。

「作ってもらう」のではなく、「相談しながら育てる」。

APPENDIX A ／ 進め方

短いやり取りを、何度も回す

相談

実装

その場で動くものが出てくる

コードが書かれ、すぐ試せる。気に入らなければ言い直す。1回で完成させようとしないのがコツ。

記録

決めた理由・やめた理由を残す

APPENDIX A ／ 実例

こう言ったら、こうなった

伝えたこと起きたこと

APPENDIX B ／ 評価

AIから見た、この進め方の評価

実際に手を動かした側から見て、この開発が最後まで崩れなかった理由は、次の6点にあります。

出口から逆算していた

15分単位・案件×作業内容という粒度は、「月次報告書へ転記する」という出口から決まっている。作りながら仕様が揺れなかった最大の理由。

要件を小分けに出した

一度に全部を伝えず、1機能ずつ。手戻りが小さく、毎回「動くもの」が残った。大きく作ってから直すより速い。

やめる判断が早い

exe化もスタートアップ登録も、使えないと分かった時点で撤退。粘らずに戻し、試した記録だけ残した。

自動化の線引きが的確

月1回の転記は手作業のまま。毎回繰り返すもの（検証・マニュアル・画面撮影）だけを自動化した。何でも自動化しなかった。

データを閉じ込めなかった

CSVとテキストだけ。専用の形式もデータベースも使っていないので、この道具が無くなっても記録は読める。

使う人と作る人が同じ

使って感じた違和感が、その日のうちに修正になる。ふつうの開発では失われる速さが、そのまま活きた。

APPENDIX B ／ わかったこと

やってみて、分かったこと

  • 完璧な仕様はいらない — 使いながら決めるほうが、結果的に早く、実態に合う。
  • 環境の制約は、自分にしか分からない — 「exeは実行できない」「スタートアップは使えない」。伝えて初めて設計に反映される。
  • 確認の仕組みとドキュメントを一緒に作らせる — 安心して直せるようになり、半年後の自分が助かる。
  • 読めることが、そのまま速さになる — 出てきたものを確かめられるので、細部まで指示しなくても任せられる。自分で書くより速い。
  • AIは決めてくれない — 何を作るか、どこでやめるかを決めるのは、いつも人間の側。

道具を自分で作る敷居は、もう高くない。

※ このスライドと利用マニュアルも、同じやり方で作成しています。

APPENDIX C ／ 他のAIとの比較

他のAIでも、作れたのか

コードを書くこと自体は、いまの主要なAIならどれも書けたはずです。
分かれ目は「自分のPCで動かして、結果を見て、直す」——このループを回せるかどうかでした。

AIの使い方どこまでできたか
チャットだけで使う ChatGPT ／ Gemini ／ Claude（ブラウザ版）／ Grok ／ Microsoft Copilot 中核機能は作れたはず。ただし貼り付け → 実行 → エラーを書き戻す作業が、すべて手動になる。コードが読める人ほど、この往復が重く感じる
コード実行つきチャット ChatGPT のデータ分析 ／ Gemini のコード実行 ほぼ戦力にならない。隔離された環境なので、WindowsのGUIも手元のファイルもExcelも触れない
エディタの補完機能 GitHub Copilot（補完）／ Cursor のタブ補完 ／ Amazon Q Developer 書く速度は上がるが検証のループがない。方式変更や不具合の切り分けは人力のまま
エージェント型のツール Claude Code（今回はこれ） ／ Cursor（Agent）／ Cline ／ Windsurf ／ Google Antigravity ／ GitHub Copilot（エージェントモード）／ Codex CLI ／ Gemini CLI ／ Devin 今回の作業の大半が再現できたはず。境界線は「この形式かどうか」で、その中では大きな差はない

APPENDIX C ／ 境界線

効いたのは「書く」以外の作業

今回、Claude Code が人の手を借りずに行った作業

  • スクリプトを実行し、検証結果を読んで直す
  • exe化を試し、実行がブロックされる原因を切り分ける
  • デスクトップやスタートアップのショートカットを作成・削除する
  • Excelを操作してマニュアルを生成、アプリを起動して画面を自動撮影

どのAIでも変わらないこと

「exeは実行できない」「スタートアップは使えない」——会社のルールは、伝えて初めて設計に反映される。休憩の仕様を3回変えたのも、使ってみた本人の判断だった。

道具の差は「実行できるか」。
中身の差は、やはり人が決める。

APPENDIX D ／ 自己評価

使いこなしは、どの段階にあるか

「使いこなし率◯％」を測る客観的な物差しは、いまのところ存在しません。
代わりに、AIとの付き合い方を5つの段階に分けて、今回どこまで来たかを振り返ります。

段階1

聞く

分からないことを質問する。調べものの相手として使う。

段階2

書かせる

文章やコードを作らせる。出てきたものは自分で確かめ、自分で動かす。

段階3

任せる

実行と検証まで任せる。こちらは「どう動いてほしいか」と「うまくいっていない点」を伝える役に回る。

段階4

仕組みにする　← 今回はここ

繰り返す作業を自動化し、決めた理由を記録に残す。動作確認・マニュアル生成・画面撮影まで仕組みに組み込んだ。

段階5

広げる　← 着手したところ

自分だけの道具で終わらせず、他の人が使える形にする。この資料と利用マニュアルが、その最初の一歩。

APPENDIX D ／ 到達点

数字ではなく、行動で確かめる

「AIをうまく使えているか」は、次の6つで測れると思います。特別なことではなく、どれも人に仕事を頼むときと同じです。

  • 目的を自分の言葉で言えるか — 何に困っていて、どうなれば成功かを説明できる。 今回：最初の2通で、前回入力の保持・CSVへの蓄積・Excelへ貼る流れまで伝えていた
  • 解き方を自分で決められるか — 提案を鵜呑みにせず方式を選び、やめる判断もできる。 今回：AIに書かせる案から、15分ごとの入力バッチへ切り替えた
  • AIが知らない前提を渡せるか — 環境・社内ルール・これまでの経緯は、外からは見えない。 今回：「exeは実行できない」「スタートアップは使えない」
  • 出てきたものを検収できるか — 動かして確かめる。読んで違和感に気づく。 今回：文字の折り返しの気持ち悪さを、CSSの指定（max-width）が原因だと特定して指摘した
  • 渡していい情報の線引きができるか — 出せない情報を、渡さない・資料に載せない。 今回：画面写真の案件名をダミー値へ差し替えた
  • 一度きりにせず、仕組みと記録に残せるか — 次に触る人（半年後の自分を含む）が困らない形にする。 今回：動作確認・マニュアル生成・画面撮影を、繰り返せる形にした

問うべきは「何％使えているか」ではなく、
「どこまで任せて、どこで自分が判断するか」。
